## What is actually left

### #0351 EDIT 4 — the `workspace` kwarg, and #0334's fix only covered half of it

`#0334` changed the `delete_app` snippet to derive the workspace from
`BIOENGINE_WORKER_SERVICE_ID` instead of `$HYPHA_WORKSPACE`. That fixes the **artifact id**. It
leaves the derived workspace being passed to `connect_to_server`, and that is the half that fails.

Measured against `hypha.aicell.io` with the repo's own token (which encodes
`ws-user-github|49943582`):

```
no workspace kwarg                        OK, landed in ws-user-github|49943582
workspace = ws-user-github|49943582       OK            <- CONTROL, the covered case
workspace = ws-u-2db9981b455e4baf         FAIL ConnectionAbortedError
workspace = bioimage-io                   FAIL ConnectionAbortedError
workspace = ws-definitely-not-a-real-...  FAIL ConnectionAbortedError
```

```
Failed to authenticate user: Current workspace encoded in the token
(ws-user-github|49943582) does not match the specified workspace (<the one you passed>)
```

So it fails at **connect** time, before any permission is consulted. The reporter's token encoded
`ws-u-2db9981b455e4baf` while the worker lived in `ws-user-github|49943582`, which is exactly
row C.

**Two corrections to #0351's own framing, both measured:**

1. It is **not** a permission error and does not read like a revoked token. It is a
   `ConnectionAbortedError` that names both workspaces explicitly. Clearer than the row claims,
   which is worth knowing because it changes how the fix is justified: the kwarg goes because it
   is unnecessary, not because its failure is confusing.
2. The hazard is at **two** sites, not one. `SKILL.md:863` (§ Call an app) hardcodes
   `"workspace": "bioimage-io"`, which fails for every token that does not encode `bioimage-io`.
   Nobody reported that one.

The kwarg is unnecessary at both, and that half is measured too rather than assumed. From a
connection made with **no** `workspace`, landing in `ws-user-github|49943582`:

```
get_service("public/artifact-manager")                   OK
am.read(artifact_id="bioimage-io/model-runner")          OK  -> alias model-runner, type application
```

The second is the one that matters: a fully-qualified id reached into `bioimage-io`, a workspace
the connection was not in and the token does not encode. (A third probe, `am.list(parent_id=
"bioimage-io/bioengine-apps")`, failed — but on a parent id that does not exist, not on
permission, so it is not evidence either way and is recorded here so it is not mistaken for some.)

`SKILL.md:1009`, the feedback-report example, already connects without the kwarg and then reaches
`public/artifact-manager`, so the document contained the working pattern all along and contradicted
itself twice.

### #0344 EDIT A residual — the current text steers toward the harmful fix

`SKILL.md:528` says the refusal *"names the ceiling and lists every existing version, so recovery
is a one-line `manifest.yaml` edit either way."* Read against a **stranger's** artifact that is a
recommendation to bump the version, which publishes your bundle as the new head of a lineage you
do not own. Needs the "pick a different id" branch, plus the point that `apps validate` cannot
ever grow the check (the CLI's `validate` takes only `app_dir`, so it has no workspace to look in).

### #0344 EDIT C — the window is documented, scoped to the wrong case

`:500` says confirm behaviourally. `:504` and `:924` both scope the ~10 to 15 s unavailable window
to a **frontend-only** redeploy. A probe fired after a Python-path update therefore has no warning
attached. Write the tolerance; do **not** reuse the ~10 to 15 s figure for the Python path, which
nobody measured.

**One correction to the row's framing.** #0344 describes this as the `skimage.data.human_mitosis()`
image, and the new section does **not** say so, because that could not be confirmed and the one
version available here contradicts it: on scikit-image 0.21.0 `human_mitosis` loads
`data/mitosis.tif`, and `AS_09125_050116030001_D03f00d0.tif` is not in that version's registry at
all. The upstream `_fetchers.py` path 404s, so the mapping could not be checked against current
scikit-image either. The file is certainly *in* scikit-image's data repository — the URL is — but
which accessor returns it is version-dependent and unverified, so the section pins the filename
and drops the accessor name. Nothing else in the edit depends on it.

A side-effect worth keeping: the attempt to verify it **is** the evidence for the paragraph's
pooch argument. With scikit-image installed and pooch absent, `skimage.data.human_mitosis()`
raised `ModuleNotFoundError` naming pooch rather than returning an array.
