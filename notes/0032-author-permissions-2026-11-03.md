# #0032 / #0033: "match on email, not name" means two opposite things

One request bundled two asks that look like the same principle and are not. Split into #0032
(permissions, done) and #0033 (My Artifacts listing, paused on a decision).

## The measurement that decided the split

Live `bioimage-io/bioimage.io`, 293 committed children, 2026-11-03:

    Daniel Franco-Barranco matched by NAME      81
    Daniel Franco-Barranco matched by EMAIL     15
    matched by EITHER (what ships today)        81

    author entries in the collection           511
    author entries carrying an email            45   (8.8%)
    artifacts with ANY author email             26 / 293
    artifacts with an email on the FIRST author 21 / 293

Script: `/tmp/measure-0032.py` (artifact-manager `list` over the REST endpoint, BIOIMAGE_IO_TOKEN).

An author entry usually carries `github_user` with a null `email`; a Google-backed Hypha session
carries an email and no GitHub handle. The two sides never meet, which is why `artifactOwnership.ts`
matches on display name and why removing that would take the contributor PR #113 was written for
from 81 rows back to 15.

## Why the same rule is right for permissions and wrong for the view

A name is a weak key. In a private VIEW a collision costs one extra row of an artifact that is
publicly listed anyway and grants nothing. In a permission it would hand write access to a stranger
who shares a name. So `roles.ts` is email-only and must stay that way; `artifactOwnership.ts` is
not, deliberately.

The email-only half of the request needed no code: `contributorEmails()` already skipped entries
without an email. Only the author narrowing was real.

## The negative control is the whole evidence

5 new tests in `roles.test.ts`, run against the pre-fix body of `contributorEmails()` (the two
`collect()` calls restored verbatim):

    Tests: 4 failed, 7 passed, 11 total

4 of 5 discriminate. The fifth pins the revoke GUARD, which the narrowing does not change but could
have broken, so it is expected to pass both ways. A new test that passes before the fix as well as
after is only worth keeping if you can say which of those two it is.
